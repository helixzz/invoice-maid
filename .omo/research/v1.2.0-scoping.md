## Theme 1: Invoice Type Taxonomy

### Current state (production DB snapshot, 2026-05-08)

All 250 invoices are Chinese VAT variants:

| invoice_type | count | Chinese sellers | 20-digit invoice_no |
|---|---|---|---|
| 电子发票（普通发票） | 208 | 207 | 208 |
| 电子发票（增值税专用发票） | 27 | 27 | 27 |
| 电子发票（铁路电子客票） | 7 | 3 | 7 |
| 增值税电子普通发票 | 6 | 6 | 0 |
| 增值税普通发票 | 2 | 2 | 0 |

- **0 NULLs, 0 empty strings** — every invoice has a type
- **0 foreign sellers** (no "Inc" / "LLC" / "Ltd")
- **96.8%** have the 20-digit 数电票 number format

### Schema facts (from explore agent report)

- `invoice_type: Mapped[str] = mapped_column(String(128))` — NOT NULL, **no enum constraint**, **no DB CHECK**
- `VALID_INVOICE_TYPES` frozenset in `app/schemas/invoice.py:10-18` lists 26 hardcoded Chinese values (including numeric codes "01", "03", "04" per 数电票 conventions)
- **Critical existing decoupling**: `InvoiceExtract.is_valid_tax_invoice: bool` (schemas/invoice.py:38-50) already exists and is orthogonal to `invoice_type`. The `is_valid_tax_invoice=False` path already works in principle — current rejection logic in `manual_upload.py:322-338` checks BOTH type-in-VALID AND is_valid_tax_invoice. Rewriting to check `is_valid_tax_invoice` alone would unlock non-VAT save paths without any schema change.
- `app/prompts/extract_invoice.txt` has 22 hardcoded Chinese VAT types in its "VALID TYPES" section — non-VAT extraction would need prompt revision
- FTS5 already indexes `invoice_type` — search / filter "just works" once values exist
- Frontend (`InvoiceListView.vue`) has **no type filter UI today**

### Design decision pending (deferred to v1.2.0)

**Option A — Structured enum** (DB CHECK constraint, e.g., `vat_invoice` / `receipt` / `proforma` / `saas_invoice` / `manual_receipt` / `other`):
- Pros: lint-time correctness, stats consistency, UI dropdown is trivial
- Cons: migration on all 250 prod rows, breaks forward-compat with new types

**Option B — Freeform with conventions** (keep VARCHAR(128), document string values):
- Pros: zero migration, LLM can extract arbitrary strings
- Cons: typo-prone, stats UI shows messy buckets

**Preferred direction**: Option A with a safety valve — add an enum AND keep a `type_label` freeform column for LLM-extracted human-readable name. The enum drives filtering/stats; `type_label` preserves the raw Chinese `电子发票（普通发票）` string for display.

### The Cursor-specific insight (user's pain point)

**Cursor is backed by Stripe.** The Cursor docs explicitly say "Invoices are manual download for now" but the download URL lives inside a Stripe-hosted session. Two concrete paths:

1. **TIER 2 bypass** — If user has their own Stripe API key AND knows the `customer` ID that Cursor assigned to them, they can call `GET /v1/invoices?customer=cus_xxx` directly and get permanent PDF URLs. No scraping. **This is the cleanest possible solution for the user's pain.**
2. **TIER 3 scrape** — Playwright login at `cursor.com/dashboard` → click "Manage Subscription" → on Stripe portal, enumerate invoices. Reference implementation: [github.com/olegam/cursor-invoice-downloader](https://github.com/olegam/cursor-invoice-downloader) — actively maintained (last push Mar 2026).

Validation needed (before designing v1.2.0): **does the user actually have a Stripe customer_id visible in their Cursor account?** If yes, TIER 2 is viable. If no, we're stuck on TIER 3. Answer determines whether v1.2.0 needs Playwright in the backend at all.

### Backend architectural facts (from explore agent report)

- `BaseEmailScanner.scan(account, last_uid, options, progress_callback) -> list[RawEmail]` is **mostly source-agnostic**. Only `from_addr` is email-specific. `RawEmail.uid`, `subject`, `attachments`, `folder`, `received_at` all work for web-scraped invoices.
- `EmailAccount` table needs **zero schema changes** to host new account types. `type` is a VARCHAR(32) string, `last_scan_uid` is polymorphic JSON. The only email-specific column is `outlook_account_type` (harmless to leave unused).
- **Precedent:** Manual upload uses a sentinel `EmailAccount` with `type="manual"` + `is_active=False`. See `alembic/0008_manual_upload_pseudo_account.py`. **Exact same pattern** works for adding `type="stripe_portal"`, `type="cursor_billing"`, etc.
- `ScannerFactory.get_scanner()` (email_scanner.py:1509-1521) is a trivial dict dispatch. Adding a new scanner is ~5 lines.
- Scheduler (`tasks/scheduler.py:706-850`) iterates ALL `is_active=True` accounts regardless of type. A new account type slots in with **zero scheduler changes**.
- Manual upload's pipeline (`services/manual_upload.py`) is **the blueprint** for non-email sources: parse → LLM enrich → dedupe → save, with synthetic `email_uid = f"manual:{scan_log.id}"`. New scrapers would use `f"stripe:{invoice_id}"`, `f"cursor:{invoice_id}"`, etc.
- **No Playwright/Selenium in the backend today.** Adding it is a new dependency and a new operational concern (headless Chromium, 200+ MB deps, security surface).

### Credentials — the sticky part

Current storage:
- `password_encrypted` (Fernet) — single plaintext string
- `oauth_token_path` — file-on-disk JSON (MSAL cache format)

Gaps for web portals:
- **No session cookie storage** (Playwright's `storageState.json`)
- **No TOTP secret storage** for automated 2FA
- **No refresh token field** for API tokens with finite TTL

v1.2.0 options:
- **Extend `email_accounts`**: add `session_state_json` (TEXT), `totp_secret_encrypted` (String(512)), `refresh_token_encrypted` (String(1024)), `token_expires_at` (DateTime). Migration adds nullable columns — zero risk.
- **New `PortalCredential` sibling table**: `(email_account_id, credential_type, credential_value, expires_at)`. Cleaner for multi-credential flows but more schema surface.

**2FA security note** (from librarian): Storing TOTP secrets in the same DB as passwords collapses 2FA to effectively 1FA if the DB is compromised. Either encrypt with a DIFFERENT key (not JWT_SECRET) or make TOTP storage opt-in with explicit operator warning.
