# v1.2.0 Track A Design: Invoice Type Taxonomy Abstraction

**Status:** Design — pending Momus review
**Date:** 2026-05-09
**Audience:** v1.2.0 implementer (single track; can be implemented in parallel with Track B)

---

## TL;DR

Today, every saved invoice in production is a Chinese VAT variant. The system **rejects non-VAT documents** with `outcome="not_vat_invoice"` (HTTP 422) at both the manual-upload path and the email-scan path.

v1.2.0 Track A adds **structured invoice category** as a first-class taxonomy:
- New column `invoice_category VARCHAR(32) NOT NULL DEFAULT 'vat_invoice'`. **Validation is enforced at the application layer (Pydantic enum), NOT via a SQL CHECK constraint** — see §2.2 for rationale (SQLite ALTER TABLE limits make application-layer enforcement the cleanest contract; a future Postgres deployment can add CHECK separately).
- Existing `invoice_type` column kept as a freeform display label (e.g., the original Chinese string `电子发票（普通发票）` or English `Stripe Invoice`)
- All 250 production invoices backfilled to `invoice_category="vat_invoice"` via Alembic migration 0015
- LLM extraction prompt rewritten to detect category + extract type label
- Validation layer (`manual_upload.py`, `scheduler.py`) decoupled from the hardcoded `VALID_INVOICE_TYPES` frozenset — non-VAT now saves with `is_valid_tax_invoice=False`
- Frontend adds multi-select category filter on InvoiceListView; stats dashboard groups by category instead of raw type
- CSV / ZIP export include both `invoice_category` and `invoice_type`

**Categories (initial enum):**
- `vat_invoice` — Chinese VAT 发票 (今日所有 250 张)
- `receipt` — Informal receipts / 收据 (no tax id, no formal invoice number)
- `proforma` — Proforma invoices (issued before payment)
- `saas_invoice` — SaaS provider invoices (Stripe / Cursor / OpenAI / Anthropic / etc.)
- `other` — Catch-all for unmatched legitimate billing documents

---

## 1. Why `invoice_category` (new column) instead of expanding `VALID_INVOICE_TYPES`

The freeform `invoice_type` field already serves as the human-readable label (e.g., Chinese `电子发票（普通发票）`, English `Stripe Invoice`). Adding `receipt` / `proforma` / `saas_invoice` to the existing `VALID_INVOICE_TYPES` frozenset would conflate three concerns:

1. **What kind of document is this** (VAT vs. receipt vs. SaaS) — needed for filtering, stats, validation logic
2. **Display string** — what the operator sees in the UI (the Chinese type name from the QR code, or `Cursor Pro Subscription` from a Stripe-issued PDF)
3. **Tax-validity flag** — `is_valid_tax_invoice` already exists for this; should be the SOLE driver of the rejection path

Today these three concerns are tangled in `invoice_type IN VALID_INVOICE_TYPES`. The fix is to separate them:

| Concern | v1.1.x today | v1.2.0 |
|---|---|---|
| Document kind / category | Implicit from `invoice_type IN VALID_INVOICE_TYPES` | Explicit `invoice_category` enum |
| Display label | `invoice_type: str(128)` | `invoice_type: str(128)` (unchanged role, broader values allowed) |
| VAT tax validity | `(invoice_type IN VALID_INVOICE_TYPES) AND is_valid_tax_invoice` | `is_valid_tax_invoice` only |

This decoupling is **the only way** to allow non-VAT invoices to reach the save path without rewriting the entire scoring logic.

## 2. Schema change

### 2.1 New column

```python
# backend/app/models/invoice.py
class Invoice(Base):
    # ... existing columns ...
    invoice_type: Mapped[str] = mapped_column(String(128))  # UNCHANGED — display label
    invoice_category: Mapped[str] = mapped_column(
        String(32), nullable=False, server_default="vat_invoice"

```

### 2.2 Alembic migration `0015_add_invoice_category.py`

```python
def upgrade() -> None:
    # Add nullable first to satisfy SQLite ALTER TABLE limitations
    op.add_column(
        "invoices",
        sa.Column("invoice_category", sa.String(length=32), nullable=True),
    )

    # Backfill all existing rows. All 250 production invoices are Chinese
    # VAT variants per the 2026-05-08 production audit.
    op.execute("UPDATE invoices SET invoice_category = 'vat_invoice' WHERE invoice_category IS NULL")

    # Tighten to NOT NULL via batch_alter_table (SQLite-compatible).
    with op.batch_alter_table("invoices") as batch:
        batch.alter_column(
            "invoice_category",
            existing_type=sa.String(length=32),
            nullable=False,
            server_default="vat_invoice",
        )

    # Index for filter queries
    op.create_index(
        "ix_invoices_invoice_category",
        "invoices",
        ["invoice_category"],
    )
```

**Authoritative validation contract (no DB CHECK):** SQLite's ALTER TABLE
does not support `ADD CHECK`. Adding a CHECK at column-creation time
would require a full table rebuild via `batch_alter_table` with
`recreate='always'` (a 250-row copy + index rebuild + 4 trigger
rebuilds), which adds risk without value: the LLM extraction layer
already constrains `invoice_category` via the Pydantic enum, and the
`PUT /invoices/{id}` endpoint uses the same Pydantic model for inbound
validation. A misbehaving direct-SQL writer (none exists in the
codebase) is the only thing a SQLite CHECK would catch, and that
threat model isn't worth the rebuild cost.

**For a future Postgres deployment** (not in v1.2.0 scope), a separate
migration would add `CHECK (invoice_category IN ('vat_invoice',
'receipt', 'proforma', 'saas_invoice', 'other'))` at zero cost. The
v1.2.0 application-layer validation is the same enum the future CHECK
would mirror, so no behavior changes when CHECK lands.

**Single source of truth for the closed enum:** `app/schemas/invoice.py`
`InvoiceCategory(str, Enum)` (see §3). Migration string literals must
match this enum exactly; `tests/test_migrations.py` will assert this
cross-file invariant.

The FTS5 virtual table currently indexes `invoice_no, buyer, seller, invoice_type, item_summary, raw_text`. Add `invoice_category` so search like `category:saas_invoice` works:

## 3. Pydantic enum + schema

```python
from enum import Enum

class InvoiceCategory(str, Enum):
    VAT_INVOICE = "vat_invoice"
    RECEIPT = "receipt"
    PROFORMA = "proforma"

        default=InvoiceCategory.VAT_INVOICE,
        description="Document kind taxonomy: vat_invoice / receipt / proforma / saas_invoice / other",
    )
    is_valid_tax_invoice: bool = Field(...)  # UNCHANGED
    # ... rest unchanged
```

The Pydantic default `VAT_INVOICE` covers cache reads — every legacy cached extraction is implicitly Chinese VAT, which matches today's production data (250/250). No cache invalidation required.

## 4. LLM prompt rewrite

`backend/app/prompts/extract_invoice.txt` currently has a hardcoded list of 22 Chinese VAT types and instructs the LLM to pick the closest match. v1.2.0 adds a category-classification step before the field extraction step:

### 4.1 New STEP 0 (category classification)

```
══ STEP 0 — DOCUMENT CATEGORY ══════════════════════════════════════════
Determine invoice_category from these signals BEFORE extracting fields:

vat_invoice — Chinese 增值税发票 / 数电票:
  • 发票号码 (invoice_no) format matches 20-digit pattern OR 8-digit legacy
  • 销售方 (seller) shows 统一社会信用代码 / 纳税人识别号
  • Document title contains 增值税 / 发票 / 电子发票
  • QR code present with 发票 metadata

receipt — Informal receipt:
  • No tax id, no formal invoice number
  • Document title is 收据 / Receipt (without tax markers)
  • Often handwritten or simple template

proforma — Issued before payment:
  • Title contains "Proforma Invoice" / "形式发票" / "PROFORMA"
  • Often labelled "NOT A TAX INVOICE"

saas_invoice — SaaS provider invoice:
  • From-address or seller name matches: stripe / cursor / openai / anthropic /
    github / aws / azure / google cloud / vercel / linear / etc.
  • Currency in USD/EUR/GBP, line items reference subscriptions/seats/usage
  • Invoice number format vendor-specific (in_xxx / INV-xxxx / etc.)

other — Legitimate billing document not matching above

Set is_valid_tax_invoice=true ONLY for vat_invoice (and only when STEP 1
PATH A or B passes). For receipt / proforma / saas_invoice / other, set
is_valid_tax_invoice=false and STILL extract fields per STEP 2.
```

### 4.2 STEP 1 (validity gate) decoupled from category

The existing PATH A / PATH B logic (which gates `is_valid_tax_invoice=true`) only runs when category is `vat_invoice`. Other categories skip directly to STEP 2 with `is_valid_tax_invoice=false`. **Critically, STEP 2 still runs** — we extract buyer/seller/amount/date for all categories.

### 4.3 STEP 2 (field extraction) — add saas_invoice currency awareness

```
amount: For saas_invoice with non-CNY currency, store the local-currency
  amount as Decimal. Currency code goes in invoice_type (e.g.,
  "USD Cursor Pro Subscription"). v1.2.0 does NOT add a separate
  currency column; the operator can disambiguate via invoice_type +
  category. (A v1.3.0 task could add `currency: str(3)` if multi-currency
  reporting becomes a real need.)
```

### 4.4 invoice_type semantics for non-VAT

| Category | Example invoice_type values |
|---|---|
| `vat_invoice` | `电子发票（普通发票）`, `增值税电子专用发票`, `数电专票` |
| `receipt` | `Receipt`, `收据` |
| `proforma` | `Proforma Invoice` |
| `saas_invoice` | `Cursor Pro Subscription`, `Stripe Invoice in_xxxx`, `Anthropic API Usage` |
| `other` | (LLM-generated short description) |

Display label stays freeform. Category drives filtering / stats.

## 5. Save-path rejection logic decoupling

### 5.1 Today (v1.1.x)

`backend/app/services/manual_upload.py:322-341`:
```python
final_type = parsed.invoice_type or ""
type_is_valid = final_type in VALID_INVOICE_TYPES or any(
    vt in final_type for vt in VALID_INVOICE_TYPES if len(vt) > 3
)
if (
    not type_is_valid
    and extracted is not None
    and not extracted.is_valid_tax_invoice
):
    return UploadResult(outcome="not_vat_invoice", ...)
```

`backend/app/tasks/scheduler.py:513-536` mirrors this logic.

### 5.2 v1.2.0 — `is_valid_tax_invoice` becomes the SOLE rejection driver for VAT-only mode

```python
# manual_upload.py
final_category = (extracted.invoice_category if extracted else None) or InvoiceCategory.VAT_INVOICE

# Rejection rule v1.2.0: only reject as not_vat_invoice when:
#   1. The classifier says it WAS targeting a VAT invoice (final_category == VAT_INVOICE), AND
#   2. The validity check failed (is_valid_tax_invoice=False)
#
# Non-VAT categories (receipt / proforma / saas_invoice / other) save normally
# with is_valid_tax_invoice=False; the category column lets operators filter.
if (
    final_category == InvoiceCategory.VAT_INVOICE
    and extracted is not None
    and not extracted.is_valid_tax_invoice
):
    return UploadResult(outcome="not_vat_invoice", ...)
```

**Migration impact on the 250 existing production invoices:** zero. They were saved under the old logic, all marked `is_valid_tax_invoice=True`; the backfill assigns `invoice_category=vat_invoice`. New rules only affect future saves.

### 5.3 The `VALID_INVOICE_TYPES` frozenset — kept, downgraded role

The frozenset stays as a **confidence boost signal in `_vat_confidence()`** (`invoice_parser.py:243`). It no longer drives the save/reject decision. This preserves the v0.9.1 confidence calibration without v1.2.0 having to rework the entire scoring system.

### 6.1 Read endpoints

|---|---|---|
| `GET /invoices` | `q, date_from, date_to` query params | + `category: list[str] = []` (multi-select), + `category_in: comma-separated string` |

Old POST/PUT request bodies missing `invoice_category` get the default value (`vat_invoice` for the existing 250 invoices' implied category, but new uploads default to whatever the LLM extracts — Pydantic default to `vat_invoice` is a fallback only).

```python
    c.setFont(font if font == "Helvetica" else font, 16)

    c.setFont(font, 11)
    y = 690
    for line in body:
        c.drawString(72, y, line); y -= 18
    c.save()
```

## 10. Rollout / rollback

### 10.1 Forward path

1. Deploy v1.2.0; migration 0015 backfills 250 rows to `invoice_category=vat_invoice` automatically (idempotent on re-run since column starts NULL only on fresh upgrade)
2. Existing UI continues to work; new category filter appears
3. New uploads start populating the column based on LLM extraction
4. Operator can re-classify any invoice via `PUT /invoices/{id}` with new category

### 10.2 Rollback (emergency)

Hard rollback to v1.1.0:
```bash
sudo /usr/local/sbin/invoice-maid-upgrade --tag v1.1.0
# Migration 0015 down: DROP COLUMN invoice_category, restore old FTS5 schema
```

The `invoice_category` column is added but NOT read by any v1.1.x code path; v1.1.0's parser ignores it. **No data loss on rollback** — column is dropped, all other invoice fields preserved. FTS5 schema rebuild is the only non-trivial part of rollback (handled by 0015 down migration; tested in `test_migrations.py`).

### 10.3 Soft rollback for non-VAT save bug

If non-VAT save reveals a bug post-deploy (e.g., the LLM mis-categorizes Chinese VAT as `other`), a temporary rule revert:

```python
# In manual_upload.py + scheduler.py, the rejection condition can be
# tightened to legacy behavior via a feature flag:
if (
    settings.STRICT_VAT_ONLY  # new env var, default False
    and final_type not in VALID_INVOICE_TYPES
):
    return UploadResult(outcome="not_vat_invoice", ...)
```

Enables operator to revert to v1.1.x rejection behavior without code rollback. Default `False` (allow non-VAT saves).

## 11. Out of scope for v1.2.0 Track A

- **Per-category confidence calibration** — `_vat_confidence()` only knows VAT signals today. Adding signals for receipt / proforma / saas would require a non-trivial rewrite. Track A keeps the existing scoring; non-VAT categories save with whatever confidence the LLM reports. Track this for v1.3.0.
- **Currency column** — punted to v1.3.0 (see §4.3).
- **Per-user category enable/disable** — instance-wide for v1.2.0; per-user is v1.3.0+.
- **Category-aware deduplication** — UNIQUE(user_id, invoice_no) stays. A SaaS invoice and a Chinese VAT invoice with coincidentally identical `invoice_no="123"` would still collide. Track this for v1.3.0; production frequency expected to be ~zero.
- **Non-Chinese VAT invoices** — categories like "EU VAT", "US sales tax receipt" are out of scope. They land in `other` until someone needs them.
