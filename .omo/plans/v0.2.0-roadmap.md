| Field | Value |
|---|---|

**Backend:**

   ```python
   class AppSettings(Base):
       __tablename__ = "app_settings"
       key: Mapped[str] = mapped_column(String(128), primary_key=True)
       value: Mapped[str] = mapped_column(Text())
       updated_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), default=utcnow)
   ```
   Keys: `llm_base_url`, `llm_api_key`, `llm_model`, `llm_embed_model`, `embed_dim`.

2. Add REST endpoints:
   - `GET /api/v1/settings/ai` — returns current AI config (API key masked as `sk-...xxxx`)
   - `PUT /api/v1/settings/ai` — updates AI config; validates by attempting a

   - `GET /api/v1/settings/ai/models` — proxy to the configured LLM provider's

   (migration-safe). Runtime reads prefer DB values over `.env` (DB wins if set).

   of directly from `Settings`. Cache the resolved config for 60s to avoid
   per-request DB lookups.

**Frontend (new "AI 模型" tab in SettingsView):**

1. Add a fourth tab to SettingsView: "AI 模型" (AI Model)
2. Form fields:
   - **API Base URL** — text input, placeholder `https://api.openai.com/v1`
   - **API Key** — password input, shows masked value from backend, editable
   - **Chat Model** — dropdown/combobox populated by `GET /settings/ai/models`
     with a "Refresh models" button; falls back to text input if model list
     fetch fails
   - **Embedding Model** — same pattern as chat model
   - **Embedding Dimensions** — number input (default 1536)
3. "Test Connection" button: calls `GET /settings/ai/models` and shows

4. "Save" button: calls `PUT /settings/ai` with all fields
5. Show current effective config source: "From database" or "From .env (default)"

**Rationale:** Currently users must SSH in and edit `.env` to change the LLM provider,

- API key is never returned in full via the API — always masked
- The `/settings/ai/models` proxy must timeout after 10s and not expose raw

- `PUT /settings/ai` with valid config → 200, DB rows updated

- `GET /settings/ai/models` proxies to upstream and returns model list
- `GET /settings/ai/models` with unreachable upstream → graceful error, not 500
- Startup seeds DB from `.env` when no DB rows exist
- Subsequent startup does NOT overwrite existing DB values
- `AIService` reads from DB when available, falls back to `.env`
- Unauthenticated requests → 401 on all endpoints

**TDD anchor (frontend):**
- AI settings tab renders form with all fields
- Model dropdown populates from API response
- "Test Connection" button calls models endpoint and shows result
- Save calls PUT and shows success/error toast
- Masked API key displays correctly (not full key)

## Deferred to v0.3.0+

### P0: Tiered Email Classification Pipeline

**Problem:** The current pipeline sends every email through the LLM API for classification.
For a mailbox with 1,000 unread emails, that's 1,000 API calls at ~$0.001–0.01 each plus
3–10 seconds latency per call. A first-scan backfill would cost $1–10 and take 1–3 hours.

**Solution:** 3-tier classification that eliminates >90% of LLM calls.

#### Tier 1 — Free local signals (instant, zero cost)

These run as pure Python functions, no network calls:

| Signal | Check | Cost | Decision |
|--------|-------|------|----------|
| Attachment filenames | `.pdf`, `.xml`, `.ofd` with invoice-like names (发票, invoice, fapiao) | 0 | → **positive** (proceed to parse) |
| Subject keywords | `发票`, `invoice`, `开票`, `报销`, `税`, `receipt` | 0 | → **positive** |
| Known sender allowlist | User-configurable domain/address list (e.g. `@tax.gov.cn`, `fapiao@`) | 0 | → **positive** |
| Newsletter headers | `List-Unsubscribe` present, or `Precedence: bulk` | 0 | → **negative** (skip) |
| No attachments + no links + no keywords | Empty signal set | 0 | → **negative** (skip) |

Expected elimination: **70–80%** of emails never leave Tier 1.

#### Tier 2 — Cheap metadata enrichment (still no LLM)

For emails that survive Tier 1 (neither clearly positive nor clearly negative):

| Signal | Check | Cost | Decision |
|--------|-------|------|----------|
| Attachment MIME types | `application/pdf`, `text/xml`, `application/ofd` | 0 | Boost positive score |
| Body URL patterns | Known invoice domains (`einvoice`, `etax`, `fapiao`) | 0 | Boost positive score |
| Email size | Very small (<1KB body, no attachments) | 0 | Boost negative score |
| Sender domain frequency | Same sender sent 50+ emails this scan → bulk sender | 0 | Boost negative score |

Use a simple scoring threshold (e.g., score > 0.6 → positive, < 0.3 → negative, between → Tier 3).

Expected elimination: **another 15–20%** resolved without LLM.

#### Tier 3 — LLM fallback (only for genuinely ambiguous emails)

Only called for the remaining ~5–10% of emails. Feed enriched context:

```
Subject: {subject}
From: {from_addr}
Attachments: {comma-separated filenames, or "none"}
Links found: {first 5 URLs from body, or "none"}
Body: {first 2000 chars of plain text}
```

This gives the LLM all cheap metadata signals it was previously missing, making its decision
more accurate on the small number of ambiguous cases.

**Expected cost/latency impact:**
- 1,000 emails → ~50–100 LLM calls instead of 1,000
- First-scan backfill: minutes instead of hours
- Ongoing scans (10–50 new emails): 0–5 LLM calls typically
