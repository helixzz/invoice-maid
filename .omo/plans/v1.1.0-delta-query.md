## TL;DR

Replace the per-folder `receivedDateTime ge <watermark>` polling in `OutlookScanner.scan()` (`backend/app/services/email_scanner.py:1145–1251`) with Microsoft Graph **delta query** (`/me/mailFolders/{id}/messages/delta`).

| Dimension | v0.9.x (current) | v1.1.0 (proposed) |
|---|---|---|
| API endpoint | `GET /me/mailFolders/{id}/messages?$filter=receivedDateTime+ge+...` | `GET /me/mailFolders/{id}/messages/delta` |
| State per folder | `"ISO_timestamp"` | `{"delta_link": "<opaque URL>", "last_sync_at": "ISO"}` |
| Boundary semantics | Re-fetches one boundary email per folder per scan, deduped downstream | Server tracks "what's new since last sync" — no boundary re-fetch |
| Soft-delete signal | None (deleted emails just stop appearing) | `@removed: {reason: "deleted" \| "changed"}` |
| Cross-folder moves | Invisible (look like delete + create after a watermark advance) | Explicit delete-in-source + create-in-destination |
| 5,000-msg cap | N/A (no `$filter` cap on plain message list) | **N/A — we drop `$filter` entirely** (was: 5,000 cap *only when `$filter` is used* on delta) |
| Resync semantics | None — just keep polling with `gt`/`ge` | `410 Gone` + `error.code = "resyncRequired"` → drop delta_link, full resync |
| Token expiry | N/A | Cache-pressure-based, no fixed TTL; expired token → `40X` + `syncStateNotFound` |

**Risk profile:** Touches the scanner that processes 4 of the user's 9 active accounts (production has Outlook accounts with up to 35,000+ messages per folder). Wrong code = silent invoice loss. Therefore: feature-flagged, runtime-bridged from legacy state, and operator kill-switch.

**Scope:** Outlook only. IMAP / QQ / POP3 unchanged.

## 1. Why now (and not in v1.0.0)

Oracle's review (session `ses_23f60d060ffevhyBG6HQGYnePm`) flagged delta query as "too high blast radius for the first 1.0 cut." v0.9.1 already shipped 8 scanner/classifier hardening changes (especially the `gt → ge` boundary fix and `includeHiddenFolders=true`); piling delta query on top of that during the same release window would have made post-deploy debugging impossible if anomalies appeared.

The post-v1.0.0 soak window (3–7 days) lets us confirm v0.9.1 is stable before introducing a structurally different scan strategy. After that, delta query becomes **safer than the current `ge` polling** because:

1. We stop guessing whether boundary emails were already processed — Graph tells us authoritatively.
2. We get explicit signal on deletions and folder moves, which currently look identical to "fell off the end of the watermark window."
3. The token is opaque; no risk of timezone or comparison-operator bugs.

## 3. New state format (with mandatory legacy bridge)

### 3.1 Format choice

```json
{
  "_format": "outlook_delta_v1",
  "folders": {
    "AAMkADk0...inbox-id": {
      "delta_link": "https://graph.microsoft.com/v1.0/me/mailFolders('inbox-id')/messages/delta?$deltatoken=ABC123...",
      "last_sync_at": "2026-04-28T03:14:15Z"
    },
    "AAMkADk0...archive-id": {
      "delta_link": "...",
      "last_sync_at": "2026-04-28T03:14:18Z"
    }
  }
}
```

**Why this shape:**

- **`_format` discriminator** — structurally distinct from every existing scanner state shape (verified):
  - IMAP/QQ: `{folder_name: {uid, uidvalidity, ...}}` (dict-of-dicts, no top-level `_format`)
  - POP3: `[message_id, ...]` (JSON array)
  - Outlook v0.9.x: `{folder_id: "ISO_timestamp"}` (flat dict-of-strings, no `_format`)
  - Outlook v1.1.0: top-level dict with `_format` key — unambiguous
- **Wrap folders in `"folders"` sub-key** — leaves room for future top-level metadata (e.g., `"_global_kill_switch"`, `"_last_resync_at"`) without colliding with folder IDs. Forward-compatible with hypothetical v2 formats.
- **Store the full `@odata.deltaLink` URL**, not just the `$deltatoken` extracted from it — Graph treats this as opaque. We don't parse, we don't reconstruct; we just GET the URL Graph hands us.
- **`last_sync_at` is debugging metadata only** — no behavior depends on it. It exists so the operator can answer "when did I last successfully delta-sync this folder?" from the DB without log archaeology.

### 3.2 Runtime bridge (no Alembic migration)

The existing scanner state is app-managed JSON in a TEXT column. We bridge at parse time, not in a DB migration. Pattern follows `_parse_imap_state()` (`email_scanner.py:345–367`):

```python
def _parse_outlook_delta_state(raw: str | None) -> tuple[dict[str, dict[str, str]], bool]:
    """Returns (state, is_legacy_v0_9).
    
    Three input shapes:
      * v1.1.0 new format: {"_format": "outlook_delta_v1", "folders": {...}}
      * v0.9.x legacy: {folder_id: "ISO_timestamp"} → bridged to {folder_id: {"_legacy_received_dt": "ISO"}}
      * Pre-v0.9.0 legacy ("__legacy_uid__"): {"__legacy_uid__": "internetMessageId"} → empty state, force one full resync
      * None / empty / malformed JSON: empty state, force full initial sync
    """
    if not raw:
        return {}, False
    try:
        data = json.loads(raw)
    except (TypeError, ValueError, json.JSONDecodeError):
        return {}, False
    if not isinstance(data, dict):
        return {}, False
    
    # v1.1.0 new format
    if data.get("_format") == "outlook_delta_v1":
        folders = data.get("folders", {})
        if isinstance(folders, dict):
            return {str(k): dict(v) for k, v in folders.items() if isinstance(v, dict)}, False
        return {}, False
    
    # Pre-v0.9.0 legacy bare-string shape
    if "__legacy_uid__" in data:
        return {}, False  # No usable per-folder state; will trigger full initial sync
    
    # v0.9.x legacy: flat dict of folder_id → ISO timestamp
    if all(isinstance(v, str) for v in data.values()):
        return {
            fid: {"_legacy_received_dt": ts, "delta_link": "", "last_sync_at": ""}
            for fid, ts in data.items()
        }, True
    
    return {}, False
```

The `is_legacy_v0_9` boolean drives **exactly one** "bridge scan" per folder per upgrade — see §4.2.

### 3.3 What the bridge does NOT do

- **Does not preserve receivedDateTime watermarks across the bridge.** The first delta call after upgrade returns *all current messages in the folder*, not "messages newer than `_legacy_received_dt`". The watermark is informational only post-bridge — used to short-circuit emails the dedup layer would have rejected anyway, but never to skip a Graph API call.
- **Does not delete the legacy state from the DB row.** We rewrite the whole state on the next successful scan — atomic, no partial-bridge risk.
- **Does not run for accounts where `last_scan_uid` is NULL.** Those are first-scan accounts; they take the normal initial-sync path.

## 4. The `OutlookScanner.scan()` rewrite

### 4.1 Method-level contract (unchanged, plus one addition)

| Concern | Behavior |
|---|---|
| Signature | `async def scan(account, last_uid=None, options=None, progress_callback=None) -> list[RawEmail]` — identical to v0.9.x |
| `self._last_scan_state` | Set to the new v1.1.0-format JSON before return |
| **`self._scan_events`** (NEW) | A `list[dict]` set to `[]` at scan entry, appended to during scan, drained by scheduler after scan completes. See §4.6 for the event contract and scheduler integration. |
| Progress callback | Same shape (`total_folders`, `current_folder_idx`, `current_folder_name`, etc.) — see §6 for the new `folder_fetch_msg` content |
| Exception contract | Same (let `httpx.HTTPError` / `OUTLOOK_CONNECTION_ERRORS` propagate; scheduler logs) **with one new caught exception** (§5) |
| Email list returned | Metadata-only `RawEmail`, `is_hydrated=False`, deduped across folders by `internetMessageId` (§4.4) |

### 4.2 Per-folder branching logic

Inside the `for folder in folders` loop (replaces lines 1170–1248):

### 4.3 The three `_delta_fetch_*` helpers

All three share an inner pagination loop. Differ only in the initial URL and the resync-on-410 contract.

#### 4.3.1 Inner pagination loop (shared)

```
url = initial_url
new_delta_link = ""
fetched: list[RawEmail] = []

while url:
    response = await client.get(url, headers={**headers, "Prefer": f"odata.maxpagesize={DELTA_PAGE_SIZE}"})
    
    if response.status_code == 410:
        body = response.json().get("error", {})
        if body.get("code") == "resyncRequired":
            raise DeltaResyncRequiredError(folder_id=folder_id, code=body.get("code"), message=body.get("message", ""))
    
    response.raise_for_status()
    payload = response.json()
    
    for item in payload.get("value", []):
        if "@removed" in item:
            # v1.1.0 ignores deletes — invoice-maid never deletes saved invoices
            # in response to upstream mailbox deletes (operator must do that
            # via the UI). We log this for operator visibility but take no
            # action on the local Invoice / file. See §7.2 for rationale.
            _log_removed_message(item, folder_id)
            continue
        
        email_obj = _build_raw_email_from_graph_item(item)
        # cross-folder dedup as in v0.9.x line 1209
        if email_obj.uid in seen_message_ids:
            continue
        seen_message_ids.add(email_obj.uid)
        fetched.append(email_obj)
    
    if "@odata.nextLink" in payload:
        url = payload["@odata.nextLink"]
    elif "@odata.deltaLink" in payload:
        new_delta_link = payload["@odata.deltaLink"]
        break
    else:
        # Defensive: malformed response; treat as end of round, no new deltaLink
        logger.error("Outlook delta: response has neither nextLink nor deltaLink for folder %s", folder_id)
        break

return fetched, new_delta_link
```

#### 4.3.2 `_delta_fetch_incremental(delta_link)`

`initial_url = delta_link` (the URL we stored last time, opaque). Calls inner loop. On `DeltaResyncRequiredError`:

```python
except DeltaResyncRequiredError:
    # Token invalidated server-side. Fall through to a fresh initial sync.
    # Log via the scanner event buffer (§4.6) — the scheduler will drain
    # these into ExtractionLog rows after scan() completes, because the
    # scanner has no DB session of its own.
    self._scan_events.append({
        "kind": "delta_resync",
        "folder_id": folder_id,
        "error_detail": f"[DELTA_RESYNC] folder={folder_id} 410 Gone; restarting with fresh delta token",
    })
    return await _delta_fetch_initial(client, headers, folder_id, FIRST_SCAN_LIMIT, ...)
```

#### 4.3.3 `_delta_fetch_bridge(folder_id, legacy_dt)`

```
initial_url = (
    f"{GRAPH_BASE_URL}/me/mailFolders/{folder_id}/messages/delta"
    f"?$filter=receivedDateTime+ge+{legacy_dt}"
)
```

This is the **only** place we use `$filter` on a delta endpoint. Per Microsoft docs, this caps the result at 5,000 messages per round — which is why we DO NOT use it for the steady-state incremental path. For the bridge it's correct: a freshly-upgraded account scanning since its v0.9.x watermark will have far fewer than 5,000 messages in 99% of cases (the watermark advanced on every prior scan).

After the bridge call returns, we have a fresh `@odata.deltaLink` and from then on the folder uses §4.3.2 forever.

**Edge case:** if the bridge round hits the 5,000 cap (returns `@odata.nextLink` indefinitely without ever producing `@odata.deltaLink`), we fall back to **full initial sync (§4.3.4)**. Detected by: completed 30 page-fetches without seeing `@odata.deltaLink`.

```python
MAX_BRIDGE_PAGES = 30  # 30 × 100 = 3000 messages, well under the 5000 cap
if pages_fetched >= MAX_BRIDGE_PAGES and not new_delta_link:
    logger.warning("Outlook delta bridge for folder %s exceeded MAX_BRIDGE_PAGES; falling back to initial sync", folder_id)
    self._scan_events.append({
        "kind": "delta_bridge_overflow",
        "folder_id": folder_id,
        "error_detail": f"[DELTA_BRIDGE_OVERFLOW] folder={folder_id} bridge exceeded {MAX_BRIDGE_PAGES} pages; falling back to initial sync",
    })
    return await _delta_fetch_initial(client, headers, folder_id, FIRST_SCAN_LIMIT, ...)
```

#### 4.3.4 `_delta_fetch_initial(folder_id, limit)`

`initial_url = f"{GRAPH_BASE_URL}/me/mailFolders/{folder_id}/messages/delta"` (no `$filter`, no `$orderby`).

Uses the existing `FIRST_SCAN_LIMIT` constant (already in v0.9.x for the same reason: don't pull a 35,000-message archive on first scan). Once `FIRST_SCAN_LIMIT` is reached, **we still keep paginating until we hit `@odata.deltaLink`** because we need the deltaLink to bookmark our position — but we stop emitting emails to the scheduler. This is a behavioral difference from v0.9.x, where first scan stopped fetching at the limit. Acceptable because:

- We're not parsing or downloading attachments for the over-limit emails; just fetching metadata pages.
- Without the deltaLink we can't do incremental sync — defeats the purpose.
- Pagination is fast (~10 pages/sec at 100 emails/page).

```python
EMIT_LIMIT_REACHED = False
for item in payload.get("value", []):
    if EMIT_LIMIT_REACHED:
        break  # don't break inner loop — see below
    email_obj = _build_raw_email_from_graph_item(item)
    if email_obj.uid in seen_message_ids:
        continue
    seen_message_ids.add(email_obj.uid)
    fetched.append(email_obj)
    if len(fetched) >= limit:
        EMIT_LIMIT_REACHED = True
# IMPORTANT: do NOT break the outer while; keep paginating until deltaLink
```

### 4.4 Cross-folder deduplication

v0.9.x uses an in-memory `seen_message_ids: set[str]` (line 1209) that persists for the duration of one `scan()` call but is discarded after. **Keep this exactly as-is.** Reasons:

- Cross-folder duplicates within one scan are a Graph quirk (e.g., the same message appearing in INBOX and All Mail) — same root cause, same fix.
- The downstream invariant (`UNIQUE(user_id, invoice_no)` on `Invoice`) catches *any* duplicate eventually.
- Per-folder delta tokens advance independently, so cross-folder dedup is purely intra-scan optimization.

### 4.5 `_build_raw_email_from_graph_item`

Identical to the v0.9.x in-line block at `email_scanner.py:1219–1238`. Extract verbatim into a private function — no behavior change. Selecting fields requires `$select` to match v0.9.x:

```
$select=id,internetMessageId,subject,bodyPreview,from,receivedDateTime,hasAttachments
```

**This `$select` works on `/messages/delta` and is recommended.** Per Microsoft docs: "Specify in the initial request only; it gets encoded into the token." So we set it once on the initial URL of every fetch helper (`_delta_fetch_initial`, `_delta_fetch_bridge`) and Graph carries it through `nextLink`/`deltaLink` for free.

### 4.6 Scanner event buffer & scheduler drain (the logging mechanism)

**Problem.** The scanner has no DB session and no `scan_log_id` — it's pure async HTTP + in-memory state. Yet we want scanner-level anomalies (`delta_resync`, `delta_bridge_overflow`) to surface as `ExtractionLog` rows so operators see them in the Settings → Scan Operations panel. Calling `_record_extraction_log()` directly from inside the scanner (as an earlier draft suggested) is a layering violation — that helper lives in `scheduler.py:197–227` and needs both the DB session and the current `scan_log_id`.

**Solution.** Mirror the existing `_last_scan_state` pattern. The scanner owns a small in-memory buffer; the scheduler reads it after `scan()` returns and persists it.

**Scanner side (`backend/app/services/email_scanner.py`)**

```python
# In OutlookScanner.scan(), immediately after __init__-like state reset:
self._scan_events: list[dict[str, Any]] = []

# Wherever an anomaly is detected (§4.3.2, §4.3.3):
self._scan_events.append({
    "kind": "delta_resync",                                    # maps to ExtractionLog.outcome
    "folder_id": folder_id,                                    # serialized into error_detail for now
    "email_uid": None,                                         # these events are not email-level
    "email_subject": "(scanner diagnostic: delta resync)",     # placeholder for the per-email card title
    "error_detail": "[DELTA_RESYNC] folder=... 410 Gone; ...",
})
```

**Event schema (all fields optional except `kind`):**

| Field | Type | Maps to `ExtractionLog.*` |
|---|---|---|
| `kind` | str | `outcome` |
| `email_uid` | str \| None | `email_uid` (default synthetic `f"scanner:{kind}:{folder_id}"`) |
| `email_subject` | str | `email_subject` |
| `attachment_filename` | str \| None | `attachment_filename` |
| `error_detail` | str | `error_detail` (already truncated to 2000 chars by `_truncate_error_detail`) |
| `folder_id` | str | NOT persisted directly; included in `error_detail` for operator visibility |

**Scheduler side (`backend/app/tasks/scheduler.py:~775`)**

Add ~12 lines immediately after the `emails = await scanner.scan(...)` block, before the existing `scan_state = getattr(scanner, "_last_scan_state", None)` block at line 819:

```python
# Drain scanner-emitted diagnostic events into ExtractionLog rows.
# Scanners (like OutlookScanner with delta query) record anomalies they
# can't persist directly because they have no DB session.
scanner_events = getattr(scanner, "_scan_events", None) or []
for event in scanner_events:
    db.add(_record_extraction_log(
        user_id=account.user_id,        # REQUIRED (enforced by signature at scheduler.py:199)
        scan_log_id=log.id,             # REQUIRED (enforced by signature at scheduler.py:200)
        email_uid=event.get("email_uid") or f"scanner:{event.get('kind')}:{event.get('folder_id', '')}",
        email_subject=event.get("email_subject") or "(scanner diagnostic)",
        attachment_filename=event.get("attachment_filename"),
        outcome=event["kind"],
        error_detail=event.get("error_detail"),
        # classification_tier / parse_method / parse_format / invoice_no /
        # confidence / download_outcome omitted — these events are not
        # email-level and have no classification / parse / download history.
    ))
```

The existing `_record_extraction_log()` signature at `scheduler.py:197–227` takes `user_id: int`, `scan_log_id: int`, `email_uid`, `email_subject`, `attachment_filename`, `outcome`, and optional diagnostic fields. Both `user_id` and `scan_log_id` are **required keyword-only arguments** (enforced by the `*` separator on line 198); omitting them is a `TypeError` at call time. `user_id` comes from `account.user_id` (the in-scope `EmailAccount` the scheduler is processing); `scan_log_id` comes from `log.id` (the `ScanLog` row the scheduler created earlier in this iteration).

**Why events are a list (not a single attr):** a single `scan()` can emit multiple events — e.g., two folders both hitting 410 in one round, or a bridge overflow in folder A followed by a delta resync in folder B. A list preserves all of them with stable ordering.

**Why not use the `progress_callback` instead:** the progress callback is for live UI progress (SSE stream → scan progress bar) and its messages are ephemeral. Persisting them to DB would couple two concerns that have different retention semantics (progress = live only; ExtractionLog = historical audit).

**Backward compatibility.** Other scanners (`ImapScanner`, `Pop3Scanner`) don't set `_scan_events`. The `getattr(scanner, "_scan_events", None) or []` handles that cleanly — no changes required to IMAP/QQ/POP3.

**Test coverage.** This drain loop itself needs a scheduler-level test: given a mock `OutlookScanner` that returns `emails=[]` and sets `_scan_events=[{"kind": "delta_resync", ...}]`, assert that exactly one `ExtractionLog` row is persisted with `outcome="delta_resync"` and `scan_log_id == log.id`. See §8.2 test case #12 (added).

## 5. Error handling additions

### 5.1 New custom exception

In `email_scanner.py` near line 107 (where `OUTLOOK_CONNECTION_ERRORS` is defined):

```python
class DeltaResyncRequiredError(Exception):
    """Raised when Graph returns 410 Gone with error.code = "resyncRequired"
    on a delta endpoint. Signals that the stored delta_link is invalid and
    a fresh initial sync is required for that folder."""
    
    def __init__(self, folder_id: str, code: str, message: str):
        self.folder_id = folder_id
        self.code = code
        super().__init__(f"[{code}] folder={folder_id}: {message}")
```

Caught only inside `_delta_fetch_incremental` (§4.3.2). Not in `OUTLOOK_CONNECTION_ERRORS` — that tuple is for *connection* failures; this is a *protocol-level* state-reset signal. Wrong abstraction.

### 5.2 New ExtractionLog outcomes (additive, persisted by scheduler drain of `_scan_events`)

We add two outcome values; existing values unchanged. Both are persisted by the scheduler's scan-event-drain loop (§4.6), **not** by the scanner directly (which has no DB session).

| New outcome | Emitted when | `error_detail` format | Persistence path |
|---|---|---|---|
| `delta_resync` | A folder's delta_link returned 410 + `resyncRequired`, recovered via fresh initial sync | `[DELTA_RESYNC] folder={folder_id} 410 Gone; restarting with fresh delta token` | Scanner appends to `self._scan_events`; scheduler drains after `scan()` returns |
| `delta_bridge_overflow` | v0.9.x→v1.1.0 bridge scan exceeded `MAX_BRIDGE_PAGES` and fell back to full initial sync | `[DELTA_BRIDGE_OVERFLOW] folder={folder_id} bridge exceeded {N} pages; falling back to initial sync` | Same path as above |

**Do NOT** add an outcome for `@removed` — those are normal delta events, not anomalies. Log them at INFO level only (see §7.2), not via the scan-events buffer.

These outcomes are **operator-visible in the existing scan-log expanded panel** (`SettingsView.vue` Fix 8 from v1.0.0 already renders any outcome string). The frontend will render them as unknown outcomes (rank 0 in `OUTCOME_PRIORITY`, falling into the "not_invoice" bucket of `summarizeEmails`). That's fine for an MVP — these are rare events. If they become noisy, add explicit handling in `scanAggregation.ts` in v1.1.1.

### 5.3 What we do NOT catch

- **401 from token expiry mid-scan** — propagate. Same as v0.9.x. Scan fails, scheduler logs, next scan re-acquires token. Fixing this requires a token-refresh-mid-scan loop that's out of scope for v1.1.0.
- **Generic 5xx** — propagate. Same as v0.9.x.
- **429 throttling** — propagate. Per Microsoft, delta queries are *less* likely to be throttled than `$filter` polling (smaller result sets). If we hit 429s, that's a signal to add `Retry-After` handling — but in a follow-up release.
- **`@removed` entries** — handled inline (§4.3.1), logged, no action. Not an error.

## 6. Feature flags & kill-switch

### 6.1 Two new env vars in `config.py`

Insert after `ALLOW_REGISTRATION` (line 40):

```python
OUTLOOK_DELTA_ENABLED: bool = True
OUTLOOK_DELTA_FALLBACK_ON_RESYNC: bool = True
```

| Var | Default | Effect when False |
|---|---|---|
| `OUTLOOK_DELTA_ENABLED` | `True` | **Two sub-cases, evaluated per account at scan entry** (§6.2 has the authoritative code): <br>(a) If the account's stored state is **v1.1.0-format**, the scanner **skips that account and returns `[]`**, preserving the stored state byte-identical. Reason: an opaque `delta_link` has no `receivedDateTime`-compatible timestamp to feed legacy polling. <br>(b) If the account's stored state is **v0.9.x-format or NULL**, the scanner runs the preserved legacy `receivedDateTime ge` code path (the pre-v1.1.0 body of `scan()`, kept intact as the private `_scan_v09_legacy` method). <br>When the flag flips back on, case (a) accounts resume delta scanning from their preserved state; case (b) accounts continue incrementally as before. |
| `OUTLOOK_DELTA_FALLBACK_ON_RESYNC` | `True` | When False, `DeltaResyncRequiredError` propagates instead of triggering `_delta_fetch_initial`. Use only for debugging unexpected 410-loop scenarios. |

### 6.2 Precise kill-switch semantics (the ONE authoritative description)

The flag gates **fetching strategy**, not **state parsing**. At every `scan()` entry the scanner does this, regardless of the flag:

```python
parsed_v110, is_legacy_v09 = _parse_outlook_delta_state(account.last_scan_uid)
parsed_v09 = _parse_graph_state(account.last_scan_uid)  # legacy helper, unchanged

if settings.OUTLOOK_DELTA_ENABLED:
    # Use parsed_v110 (which includes bridged v0.9.x watermarks as _legacy_received_dt)
    state_in = parsed_v110
    fetch_path = "delta"
else:
    # Flag is off. We MUST still honour stored v1.1.0 state — specifically
    # the delta_link URLs — by NOT clobbering them. So we:
    #   1. Use v0.9.x-shape data derived from whatever we can salvage
    #   2. NEVER write v0.9.x-format JSON back when v1.1.0 JSON was present
    state_in = _v09_shape_from_parsed(parsed_v110, parsed_v09)
    fetch_path = "legacy_v09"
```

And at scan completion, the serializer is also aware:

```python
if fetch_path == "delta":
    # Always write v1.1.0 format
    self._last_scan_state = _serialize_outlook_delta_state({
        "_format": "outlook_delta_v1",
        "folders": state_out,
    })
else:
    # Flag-off path. If the input was v1.1.0, write it BACK unchanged
    # (plus any last_sync_at updates); never downgrade.
    if _input_was_v110_format(account.last_scan_uid):
        self._last_scan_state = account.last_scan_uid  # preserve as-is
    else:
        # Input was v0.9.x; stay v0.9.x.
        self._last_scan_state = _serialize_graph_state(state_out_v09)
```

**Net effect:** flipping `OUTLOOK_DELTA_ENABLED` false causes the scanner to **skip scanning that account until the flag is flipped back on** if the state is v1.1.0-format (we don't want to run legacy-shaped polling against an account whose last incremental state lives in an opaque delta_link — the watermarks aren't there). This is the safe default: no data loss, no duplicate deluge, just a scan pause.

For operators who want the account to actively poll via v0.9.x while the flag is off, document the manual recovery path (§6.3).

**Test case #9 updated:** with `OUTLOOK_DELTA_ENABLED=False` and v1.1.0 state on disk, assert that the scan returns `[]` and the state is written back **byte-identical** to the input.

### 6.3 Manual recovery / force-downgrade

If the operator genuinely wants legacy polling to resume on a specific account after disabling the flag (rare; debug only), they run:

```sql
UPDATE email_accounts SET last_scan_uid = NULL WHERE id = <account_id>;
```

Next scan with the flag off will do a full v0.9.x-style first scan (bounded by `FIRST_SCAN_LIMIT`). This is a one-shot, operator-initiated action — never automatic.

### 6.4 No DB-backed override (yet)

We use `.env` only. The DB-backed `app_settings` table (per `services/settings_resolver.py`) is reserved for AI/classifier settings that change frequently. Kill-switches that change once a year don't need the operational complexity of cache-with-TTL. Follow `ALLOW_REGISTRATION`'s pattern (see `api/auth.py:130–137`).

## 7. Behaviors deliberately out-of-scope

### 7.1 `Mail.Read.Shared` shared-mailbox delta

Microsoft Graph supports `/users/{id}/mailFolders/{id}/messages/delta` for shared mailboxes with `Mail.Read.Shared` scope. We currently use `Mail.Read` only (`OutlookScanner.SCOPES = ["Mail.Read"]` at line 1137). Shared mailbox support requires:

- Adding `Mail.Read.Shared` to `SCOPES`.
- Re-running OAuth device-code flow on every existing Outlook account (force re-consent).
- Adding a UI affordance to select shared mailboxes.

Out of scope for v1.1.0. Track as a v1.2.0 candidate.

### 7.2 Acting on `@removed` events

When Graph reports a message was deleted server-side, **we do not delete the corresponding local `Invoice` row.** Reasons:

- The message and the invoice are separate things — the user might delete the email (cleaning their inbox) without intending to delete the invoice (which they need for tax records).
- If we deleted invoices reactively, a single misclick on a phone-mail-app deletes the corresponding invoice forever, with no audit trail. Operationally terrifying.
- Local invoice deletion goes through the existing UI bulk-delete flow with confirmation modal.

So: `@removed` events are logged at INFO level with `logger.info("Outlook delta: message %s removed from folder %s (reason: %s)", item.get("id"), folder_id, item.get("@removed", {}).get("reason"))` and otherwise ignored.

### 7.3 Per-account delta enable/disable

Oracle's open question (handoff line 273) about per-account opt-in for accounts with very old watermarks. Punted: the bridge scan (§4.3.3) handles old watermarks correctly via `$filter=receivedDateTime+ge+...` for the *one* bridge round. After that the account is on delta and fine. Per-account toggle adds DB schema, UI controls, and edge cases without solving a real production problem we've measured. Revisit only if the bridge scan misbehaves on real production data.

### 7.4 Token refresh mid-scan

A long initial sync of a 35,000-message folder might exceed the access token's 1-hour validity. The current v0.9.x code has the same problem and doesn't handle it (token acquired once at line 1152). Fixing this requires:

- Refreshing the token before each Graph API call OR
- Catching 401 mid-loop, re-acquiring, retrying the failed page

Both add complexity. Deferred. v1.1.0 will exhibit the same failure mode as v0.9.x for very-long-initial-sync scenarios. If this becomes a real problem, v1.1.1 patches it.

class FakeDeltaClient:
    def __init__(self, response_queue: list[FakeResponse]):
        self._queue = list(response_queue)

    async def __aenter__(self): return self
    async def __aexit__(self, *_): return False

        if not self._queue:

## 11. Rollback plan

If post-deploy v1.1.0 is misbehaving:

**Soft rollback (preferred):**
1. `sudo systemctl stop invoice-maid`
2. Edit `/etc/invoice-maid/invoice-maid.env`: add `OUTLOOK_DELTA_ENABLED=false`
3. `sudo systemctl start invoice-maid`
4. Outlook scanner behaviour per §6.1/§6.2:
   - Accounts whose state is already v1.1.0-format → **skipped** (return `[]`), state preserved byte-identical for when the flag flips back on.
   - Accounts whose state is still v0.9.x-format (e.g., freshly-deployed accounts that haven't completed their first bridge) → fall through to the preserved legacy `receivedDateTime ge` polling path.
5. To force-resume legacy polling on a specific skipped account (rare operator-only recovery), follow §6.3: `UPDATE email_accounts SET last_scan_uid = NULL WHERE id = <account_id>;` — next scan will do a full v0.9.x-style first scan bounded by `FIRST_SCAN_LIMIT`.

**Hard rollback:**
```bash
sudo /usr/local/sbin/invoice-maid-upgrade --tag v1.0.1
```

The upgrade script handles backup + restore. Note the v0.9.x → v1.1.0 bridge scan already wrote new-format JSON to `last_scan_uid`. Hard rollback to v1.0.x will see this JSON and `_parse_graph_state` will return empty (current graceful degradation behavior — see §6.2). Result: one full re-scan per Outlook account post-rollback. Annoying but safe.
