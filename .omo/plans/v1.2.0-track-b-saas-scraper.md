# v1.2.0 Track B Design: SaaS Portal Scraping (Cursor-First)

**Status:** Design — pending Momus review + user input
**Date:** 2026-05-09
**Audience:** v1.2.0 implementer (parallel to Track A)
**User priority:** Cursor first — user is a Cursor team-subscription admin

---

## TL;DR

invoice-maid v1.1.x ingests invoices via **email scan** (IMAP / Outlook / QQ / POP3) or **manual upload**. v1.2.0 Track B adds a **third ingestion source: scheduled web-portal scraping**, scoped initially to **Cursor**.

Architecture:
- **`BaseScraper`** abstract class parallel to `BaseEmailScanner` (or shared base — TBD per Momus); produces `RawEmail` objects with synthetic `from_addr` like `billing@cursor.com` so the existing parse → enrich → save pipeline doesn't change.
- **`CursorScraper`** concrete implementation using **Playwright** (headless Chromium) — log in to `cursor.com/dashboard` → navigate to billing → enumerate Stripe-portal invoice links → download PDFs.
- **`EmailAccount` table extended** with four new nullable columns: `playwright_storage_state` (TEXT, JSON), `secondary_credential_encrypted` (TEXT for Fernet'd login email), `secondary_password_encrypted` (TEXT for Fernet'd login password), and `totp_secret_encrypted` (TEXT for optional TOTP seed). Existing columns unchanged.
- **Account-creation model: USER-CREATED, not pre-seeded.** Operator adds a Cursor account via the existing Settings → Add Account flow with `type="cursor"`. There is **no** Alembic-seeded sentinel row — the v0.9.0 manual-upload precedent (migration 0008's pseudo-account) was a special case for stateless single-instance uploads; Cursor accounts are per-user, can have multiple per user, and require credentials. The existing `email_accounts` schema (with the v1.2.0 column additions) is sufficient.
- **Scheduler** dispatches all `is_active=True` accounts via `ScannerFactory.get_scanner(account.type)` regardless of type. Adding `"cursor": CursorScraper()` to the dispatch dict is the only scheduler-side change.
- **Frontend** adds "Cursor.com (SaaS scraping)" option to the Settings → Add Account dropdown; new conditional fields (login email / password / optional TOTP secret / optional manual storage_state paste — see §6.5 for when the manual-paste field is shown).

**Stripe direct-API path EXPLICITLY ELIMINATED**: the user is a Cursor *customer* (a Stripe `customer` record under Cursor's merchant account), not a Stripe merchant themselves. Stripe API keys (`sk_live_*` / `rk_live_*`) are merchant-only. Only TIER 3 (web scraping) is viable for Cursor.

**LLM prompt (Track A) handles non-Chinese-VAT PDFs gracefully** — confirmed by direct inspection of `invoice_parser.py` (regex path for Chinese fails to 0 confidence → LLM fallback). v1.2.0 Track A's prompt rewrite explicitly instructs `saas_invoice` category extraction with USD/EUR/etc. amounts.

## 1. Why scrape, not email-fall-back

Cursor's official statement: ["Invoices are manual download for now"](https://cursor.com/help/account-and-billing/invoices). The user's pain point is exactly this: monthly invoices have to be manually downloaded one-by-one. The user has not received any email-attached PDFs from Cursor and cannot configure Cursor to send them.

Stripe API direct path (which would have been TIER 1 — clean) is **NOT AVAILABLE** to the user as a Cursor customer:
- Stripe API keys are issued only to merchants who use Stripe to accept payments
- The user is a customer of Cursor (a Stripe merchant)
- The user's only Stripe-side interface is the **Customer Portal session URL** that Cursor's "Manage Subscription" button generates — short-lived (minutes), not an API
- Confirmed via [Stripe Restricted API Keys docs](https://docs.stripe.com/keys/restricted-api-keys) — restricted keys are merchant-only

So Cursor is **TIER 3 by necessity**: Playwright login → navigate dashboard → follow "Manage Subscription" redirect to Stripe portal → enumerate invoices → download PDFs.

## 2. Reference implementation: `olegam/cursor-invoice-downloader`

Active project (last push 2026-03), 17 releases, Node.js + Playwright. Provides the proven URL paths and selectors. Our Python port follows the same flow:

1. Navigate to `https://cursor.com/dashboard`
2. Wait for authenticated state (cookie-based session reuse)
3. Click "Manage Subscription" button
4. Wait for redirect to `https://billing.stripe.com/p/session/{token}`
5. Scroll to billing history table
6. For each invoice row: capture invoice ID + date + amount; click "Download invoice" (or follow the PDF link directly)
7. Save PDF; record invoice ID for future dedup

The user (team admin) sees TEAM-scoped invoices via this flow. Solo accounts would see personal invoices the same way.

## 3. Architecture overview

### 3.1 Class hierarchy decision

**Option A (preferred): Separate `BaseScraper` abstract class**
- New file `backend/app/services/web_scraper.py`
- Sibling to `BaseEmailScanner`
- Same `scan(account, last_uid, options, progress_callback) -> list[RawEmail]` interface
- `ScannerFactory` dispatches both via the `type` field on `EmailAccount`

**Option B: Make `CursorScraper` inherit from `BaseEmailScanner`**
- Reuses interface but conceptually wrong (no email)

**Recommendation: Option A.** Distinct semantics, easy to extend (Stripe-portal-via-cookie-paste, AWS API integration, etc., all become `BaseScraper` subclasses). The interface contract is identical (`scan() → list[RawEmail]`), so `RawEmail` semantics stretch to "any invoice-bearing document with metadata"; we don't rename the dataclass for v1.2.0 (rename is a v2.0 breaking change).

### 3.3 ScannerFactory dispatch

```python
# backend/app/services/email_scanner.py:1976
class ScannerFactory:
    @staticmethod
    def get_scanner(account_type: str) -> BaseEmailScanner | BaseScraper:
        scanners: dict[str, BaseEmailScanner | BaseScraper] = {
            "imap": ImapScanner(),
            "pop3": Pop3Scanner(),
            "outlook": OutlookScanner(),
            "qq": ImapScanner(),
            "cursor": CursorScraper(),  # NEW
        }

```

### 3.4 Scheduler — two additive changes (Task B8)

Per the prior v1.1.0 explore agent's finding, `scan_all_accounts()` iterates `is_active=True` accounts regardless of type. `account.type="cursor"` slots in via the factory dispatch. Progress callback semantics (folders/UIDs) gracefully degrade — the scraper just emits `current_folder_idx=1, current_folder_name="Invoices", folder_fetch_msg="Cursor: 4 invoices fetched"` style updates.

Scheduler **does need two small additions** (Task B8 implements + tests):

1. After `_last_scan_state` handling, persist `scanner._updated_storage_state` back to `account.playwright_storage_state` when the scanner produced one. Without this, Cursor session reuse silently breaks — next scan would always need a fresh login.
2. The existing v1.1.0 drain loop is polymorphic and handles `kind="auth_required"` events without logic change; only test coverage extension is needed.

## 4. EmailAccount schema extensions

### 4.1 New columns (Alembic 0016)

```python
def upgrade() -> None:
    op.add_column(
        "email_accounts",
        sa.Column("playwright_storage_state", sa.Text(), nullable=True),
    )
    op.add_column(
        "email_accounts",
        sa.Column("secondary_credential_encrypted", sa.String(length=1024), nullable=True),
    )
    op.add_column(
        "email_accounts",
        sa.Column("secondary_password_encrypted", sa.String(length=1024), nullable=True),
    )
    op.add_column(
        "email_accounts",
        sa.Column("totp_secret_encrypted", sa.String(length=512), nullable=True),
    )
```

| Column | Purpose | Storage |
|---|---|---|
| `playwright_storage_state` | Persisted browser session (cookies + localStorage) | Plain text JSON (not encrypted; cookies are session tokens, encrypted in transit anyway; whoever has DB read access already has effective admin) |
| `secondary_credential_encrypted` | Login email (e.g., Cursor login email — distinct from `username` which holds the account label) | Fernet, key from `JWT_SECRET` |
| `secondary_password_encrypted` | Login password | Fernet, key from `JWT_SECRET` |
| `totp_secret_encrypted` | Optional TOTP seed | Fernet, **key from a SECONDARY env var `TOTP_ENCRYPTION_KEY`** (separate from JWT_SECRET; if absent, TOTP feature disabled and existing accounts with TOTP secrets keep them encrypted but unusable) |

### 4.2 Why `playwright_storage_state` is plain text

- Storage state is ~50KB JSON; encrypting bloats DB rows
- Stripe cookies (`__stripe_sid`, `__stripe_mid`) and Cursor's `WorkosCursorSessionToken` are bearer tokens — anyone with the DB row can already log in as the user via the cookies anyway. Encryption adds zero security in this threat model.
- Fernet has a 4KB practical limit before rows get awkward
- Compare: `oauth_token_path` is a file path on disk (also plaintext in the FS); the security model is "DB and filesystem are equivalently sensitive"

### 4.3 Why TOTP secrets need a SEPARATE encryption key

Per [OWASP NIST SP 800-63B §5.1.4.1](https://pages.nist.gov/800-63-3/sp800-63b.html), TOTP seeds are functionally equivalent to passwords and must be reversibly stored (unlike password hashes which are one-way). Storing TOTP seeds with the same key as the password would mean a single key compromise reveals BOTH factors — collapsing 2FA to 1FA.

**Mitigation:** A separate `TOTP_ENCRYPTION_KEY` env var. If it's present, TOTP is supported (encrypted at rest with that key). If absent, the column stays NULL and the operator must complete 2FA manually each session.

For v1.2.0 we **do not require operators to enable TOTP storage** — interactive re-auth flow (§7.4) is the safer default.

### 5.2 Browser lifecycle

```python
# backend/app/services/scrapers/playwright_session.py
from playwright.async_api import async_playwright, Browser, BrowserContext, Page

class PlaywrightSession:
    """Async context manager for one scrape. Reuses the persisted
    storage_state from EmailAccount.playwright_storage_state if present."""

    def __init__(self, account: EmailAccount, settings: Settings):
        self._account = account
        self._settings = settings
        self._playwright = None
        self._browser: Browser | None = None
        self._context: BrowserContext | None = None
        self._page: Page | None = None

    async def __aenter__(self) -> Page:
        self._playwright = await async_playwright().start()
        self._browser = await self._playwright.chromium.launch(headless=True)
        storage_state = (
            json.loads(self._account.playwright_storage_state)
            if self._account.playwright_storage_state
            else None
        )
        self._context = await self._browser.new_context(
            storage_state=storage_state,
            user_agent=DESKTOP_CHROME_UA,  # avoid headless detection
        )
        self._page = await self._context.new_page()
        return self._page

    async def __aexit__(self, *exc_info):
        # Persist updated storage state — Cursor refreshes cookies during session
        if self._context is not None and self._account.id is not None:
            new_state = await self._context.storage_state()
            self._updated_storage_state = json.dumps(new_state)
        if self._page: await self._page.close()
        if self._context: await self._context.close()
        if self._browser: await self._browser.close()
        if self._playwright: await self._playwright.stop()

    @property
    def updated_storage_state(self) -> str | None:
        return getattr(self, "_updated_storage_state", None)
```

The scheduler picks up `scanner._updated_storage_state` (analogous to `_last_scan_state`) and writes it back to `EmailAccount.playwright_storage_state` so subsequent scans skip login.

### 5.3 Session lifetime

Cursor's auth provider (WorkOS) issues `WorkosCursorSessionToken` cookies with multi-day TTL. Stripe Customer Portal session URLs are short-lived (minutes), but the Cursor → Stripe redirect generates a fresh portal session each time we click "Manage Subscription". So:

- **First scan:** full login flow (email + password → 2FA → save storage state)
- **Subsequent scans (≤7 days typical):** reuse storage state, skip login
- **After session expiry:** detect via "redirected to /login URL" → emit `_scan_events` event with `kind="auth_required"` → operator gets a UI prompt to re-login

## 6. CursorScraper implementation

### 6.1 scan() flow

```python
class CursorScraper(BaseScraper):
    async def scan(
        self,
        account: EmailAccount,
        last_uid: str | None = None,
        options: ScanOptions | None = None,
        progress_callback: Callable[[dict], None] | None = None,
    ) -> list[RawEmail]:
        self._scan_events: list[dict] = []
        self._last_scan_state: str | None = last_uid  # JSON: {seen_invoice_ids: [...]}
        self._updated_storage_state: str | None = None

        seen_invoice_ids = self._parse_seen(last_uid)
        new_invoices: list[RawEmail] = []

        async with PlaywrightSession(account, get_settings()) as page:
            await page.goto("https://cursor.com/dashboard")

            if await self._needs_login(page):
                await self._login(page, account)
                if await self._needs_2fa(page):
                    await self._handle_2fa(page, account)

            await self._navigate_to_billing(page)
            stripe_session_url = await self._click_manage_subscription(page)
            await page.goto(stripe_session_url)

            invoice_rows = await self._enumerate_invoices(page)
            for row in invoice_rows:
                if row.invoice_id in seen_invoice_ids:
                    continue
                pdf_bytes = await self._download_pdf(page, row)
                new_invoices.append(self._build_raw_email(account, row, pdf_bytes))
                seen_invoice_ids.add(row.invoice_id)
                if progress_callback:
                    progress_callback({
                        "folder_fetch_msg": f"Cursor: {len(new_invoices)} invoice(s) fetched",
                    })

            self._updated_storage_state = json.dumps(await page.context.storage_state())

        self._last_scan_state = json.dumps({
            "_format": "cursor_scraper_v1",
            "seen_invoice_ids": sorted(seen_invoice_ids),
            "last_scan_at": utcnow_iso(),
        })
        return new_invoices
```

### 6.2 RawEmail synthesis

```python
def _build_raw_email(self, account: EmailAccount, row: InvoiceRow, pdf_bytes: bytes) -> RawEmail:
    return RawEmail(
        uid=f"cursor:{row.invoice_id}",  # synthetic, deduped via UNIQUE(user_id, invoice_no)
        subject=f"Cursor Invoice {row.invoice_id} ({row.amount} {row.currency})",
        body_text=f"Cursor invoice for {row.period_start} - {row.period_end}",
        body_html="",
        from_addr="billing@cursor.com",  # synthetic but useful for trusted-sender check
        received_at=row.invoice_date,
        attachments=[
            RawAttachment(
                filename=f"cursor-invoice-{row.invoice_id}.pdf",
                content_type="application/pdf",
                size=len(pdf_bytes),
                payload=pdf_bytes,
            ),
        ],
        body_links=[],
        headers={
            "_scraper": "cursor",
            "_invoice_id": row.invoice_id,
            "_currency": row.currency,
            "_amount_pretty": f"{row.amount} {row.currency}",
        },
        is_hydrated=True,  # PDF already in memory; no separate hydrate step
        folder="Cursor Invoices",
        message_id=f"cursor-{row.invoice_id}",
    )
```

### 6.3 State persistence shape

```json
{
  "_format": "cursor_scraper_v1",
  "seen_invoice_ids": ["in_xxx1", "in_xxx2", "in_xxx3"],
  "last_scan_at": "2026-05-09T03:55:55Z"

```

`seen_invoice_ids` capped at 1000 entries (FIFO eviction); covers ~30 years of monthly invoices. Saved as JSON in `EmailAccount.last_scan_uid` (same column the email scanners use, polymorphic per-scanner format — same pattern as v1.1.0 Outlook delta).

### 6.4 Login flow

```python
async def _login(self, page: Page, account: EmailAccount) -> None:
    settings = get_settings()
    email = decrypt_password(account.secondary_credential_encrypted, settings.JWT_SECRET)
    password = decrypt_password(account.secondary_password_encrypted, settings.JWT_SECRET)
    if not email or not password:
        self._scan_events.append({
            "kind": "auth_required",
            "error_detail": "[CURSOR_AUTH] login required; configure credentials via Settings",
        })
        raise CursorAuthRequiredError("login credentials missing")

    # Selectors come from olegam/cursor-invoice-downloader reference impl.
    # If Cursor changes their login UI, update these selectors and bump
    # CURSOR_LOGIN_VERSION constant for cache-bust.
    await page.fill('input[type="email"]', email)
    await page.click('button[type="submit"]')
    await page.fill('input[type="password"]', password)
    await page.click('button[type="submit"]')
    # Wait for navigation away from /login OR for 2FA challenge
    await page.wait_for_load_state("networkidle", timeout=30000)
```

### 6.5 2FA handling

Two modes for v1.2.0:

**Mode A — Stored TOTP:** if `account.totp_secret_encrypted` is set AND `TOTP_ENCRYPTION_KEY` env var is present, scraper decrypts + generates code via `pyotp.TOTP(secret).now()`, fills the 2FA challenge input. Fully automated after initial setup.

**Mode B — Manual storage_state paste:** if `totp_secret_encrypted` is NULL (operator declined TOTP storage), the scraper cannot pass a 2FA challenge unattended. Instead:

1. Operator locally runs a one-shot `scripts/cursor_login_local.py` on their own machine (shipped in v1.2.0):
   ```bash
   # On the operator's machine (NOT on the production host)
   python scripts/cursor_login_local.py
   # Opens a NON-headless Chromium, operator logs in + completes 2FA by hand,
   # script saves cookies+localStorage to /tmp/cursor_storage_state.json
   ```
2. Operator copies the JSON content into the Settings → Cursor account → "Paste storage state (2FA accounts only)" textarea and clicks Save.
3. Backend Fernet-free-stores this in `account.playwright_storage_state` (it's already plaintext per §4.2 rationale).
4. Next scrape reuses the session; operator re-pastes when the session expires (~7–30 days per Cursor's WorkOS cookie TTL).

**Mode B is EXPLICITLY IN v1.2.0 SCOPE** (answers Momus's B6 concern):
- Frontend: new textarea field in SettingsView, shown only when `type === 'cursor'` AND no `totp_secret` was entered (see §7.1 below).
- Backend: `EmailAccountCreate.playwright_storage_state: str | None = None` passed through by `POST /accounts` and `PUT /accounts/{id}` directly into the DB column (no encryption per §4.2).
- Script: `scripts/cursor_login_local.py` (~30 lines of Playwright Python) uses `chromium.launch(headless=False)` + operator-driven manual login + `await context.storage_state(path=...)`.

**Interactive-in-browser login from the web UI** (ideal UX) is deferred to v1.2.1+ — requires either SSH X11 forwarding, a separate local desktop app, or a device-code-style handshake. None fit v1.2.0's scope.

## 10. Operational concerns

### 10.1 Chromium memory footprint

Headless Chromium uses 200–400 MB RAM during a scan. The systemd unit currently has no memory limit; with v1.2.0 + Cursor scrape running every 60min, peak memory will spike briefly. Add `MemoryHigh=1G` to `deploy/invoice-maid.service` to ensure systemd kills runaway processes before swapping. This is a deploy-tooling change, not a v1.2.0 code change.

### 10.2 Anti-bot measures

Cursor's WorkOS-based login does not currently use CAPTCHAs (verified empirically by the `olegam/cursor-invoice-downloader` project). Stripe Customer Portal is even more relaxed. **No `playwright_stealth` needed for v1.2.0.** If Cursor adds Cloudflare Turnstile (or similar) post-deploy, the bot detection workaround lands in v1.2.1+.

### 10.3 Rate limiting

Cursor + Stripe portal have generous rate limits for human-paced browsing. A scrape every 60min (the default `SCAN_INTERVAL_MINUTES`) is far below any plausible threshold. We **do not need to rate-limit ourselves** in v1.2.0.

### 10.4 Failure isolation

Per the v0.9.x scanner-fault-isolation precedent: a failed Cursor scan does NOT break the email scans for the same operator's other accounts. Each account is processed independently via the existing scheduler `try/except` per-account loop.
